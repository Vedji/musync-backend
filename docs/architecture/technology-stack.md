# Обоснование выбора технологического стека

## Основные требования к backend

Разрабатываемое приложение представляет собой клиент-серверную систему для хранения, синхронизации и воспроизведения пользовательской музыкальной библиотеки на нескольких устройствах.

Серверная часть приложения должна:

- хранить информацию о пользователях и устройствах;
- хранить метаданные музыкальной библиотеки;
- обеспечивать синхронизацию данных между устройствами;
- хранить музыкальные файлы отдельно от основной базы данных;
- обеспечивать потоковую передачу аудиофайлов;
- поддерживать длительные HTTP-соединения;
- работать с S3-совместимым хранилищем;
- обслуживать несколько одновременно подключенных устройств;
- предусматривать возможность дальнейшего добавления транскодирования аудио.

На основании этих требований был выбран технологический стек, ориентированный на разработку сетевого приложения с потоковой передачей данных и раздельным хранением метаданных и медиафайлов.

## Выбор языка

В качестве языка серверной части выбран Go.

Go является компилируемым языком со статической типизацией. Это позволяет явно описывать внутренние модели приложения и выявлять часть ошибок на этапе компиляции.

Стандартная библиотека Go содержит средства для работы с HTTP и потоковым вводом-выводом. Для конкурентного выполнения задач язык использует goroutine, что позволяет серверу одновременно обрабатывать несколько сетевых запросов и длительных соединений.

Такая модель соответствует характеру приложения, в котором сервер должен одновременно выполнять операции с метаданными, обслуживать клиентские запросы и передавать аудиоданные.

## База данных

Для хранения структурированных данных используется PostgreSQL.

В базе данных хранятся:

- пользователи;
- устройства;
- исполнители;
- альбомы;
- треки;
- плейлисты;
- информация о расположении медиафайлов.

Эти сущности имеют связи между собой, поэтому для их хранения используется реляционная модель данных.

## Доступ к данным

Для взаимодействия Go-приложения с PostgreSQL используется библиотека pgx.

Работа с SQL-запросами реализуется через sqlc. Запросы описываются непосредственно на SQL, после чего sqlc генерирует типизированные методы и структуры Go.

Такой подход позволяет сохранять SQL-запросы в явном виде, контролировать обращения к базе данных и уменьшать количество ручного кода для преобразования результатов запросов.

## Миграции

Для управления изменениями структуры базы данных используется goose.

Миграции позволяют последовательно изменять схему PostgreSQL по мере развития приложения. Это упрощает сопровождение базы данных и позволяет применять одинаковый набор изменений в разных окружениях.

## Объектное хранилище

Музыкальные файлы могут иметь значительный размер, поэтому их содержимое не хранится непосредственно в PostgreSQL.

В базе данных сохраняются метаданные музыкального файла и информация о его расположении, а сами аудиофайлы размещаются в объектном хранилище.

В качестве объектного хранилища используется MinIO. Он предоставляет S3-совместимый API и позволяет работать с файлами как с объектами, используя ключи и bucket.

Такое разделение позволяет использовать PostgreSQL для структурированных данных, а MinIO — для хранения медиафайлов. Это также упрощает дальнейшую работу с потоковой передачей аудио и возможным транскодированием.

## Итоговый стек

В результате для разработки серверной части выбран следующий стек:

- `Go` — серверная логика и HTTP API;
- `PostgreSQL` — хранение структурированных данных;
- `pgx` — подключение к PostgreSQL;
- `sqlc` — генерация типизированного кода на основе SQL-запросов;
- `goose` — миграции базы данных;
- `MinIO` — S3-совместимое объектное хранилище;
- `FFmpeg` — последующая обработка и транскодирование аудиофайлов;
- `Docker Compose` — локальное развертывание инфраструктурных компонентов.
